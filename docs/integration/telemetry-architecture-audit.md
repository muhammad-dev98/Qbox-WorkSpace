# QBox Telemetry Architecture Audit

## Current Architecture

Qbox-Hardware already has a health manager, heartbeat protocol objects, an MQTT
client, structured JSON logging, and a durable SQLite-backed event queue. Device
control remains owned by the hardware, camera, lock, GPIO, connectivity, and
registration modules.

Qbox-Backend already has `hardware_devices` models for device identity,
connectivity, health, commands, lifecycle, audit, MQTT credentials, and MQTT
topic helpers. It also has an older `devices_telemetry` app and an MQTT ingest
function that writes flat telemetry rows there.

## Existing Telemetry Implementation

- Hardware heartbeat payloads are generated by `qbox_platform.health.HealthManager`.
- Hardware MQTT publishing is centralized in `qbox_platform.transport.mqtt.MQTTManager`.
- Hardware durable delivery uses `qbox_platform.storage.AgentDatabase.event_queue`.
- Backend MQTT routing is in `hardware_devices/device_mqtt.py`.
- Backend health is persisted in `hardware_devices.DeviceHealth`.
- Legacy backend flat telemetry persistence uses `devices_telemetry.DeviceTelemetry`.

## Conflicts

- The existing topic helpers expose a flat `/telemetry` and `/events` topic,
  while the production contract requires typed subtopics.
- Backend MQTT ingest owns telemetry parsing in the callback file rather than a
  telemetry service.
- Legacy flat telemetry does not model components, alerts, diagnostics, event
  idempotency, or occurred/received timestamp separation.
- Component state is implicit inside health snapshots instead of first-class
  device components.

## Missing Functionality

- First-class component registry and stable component keys.
- Idempotent device event persistence keyed by device and event ID.
- Heartbeat history separate from latest health state.
- Raw telemetry persistence with bounded API queries.
- Diagnostic result persistence.
- Alert deduplication and lifecycle.
- Canonical typed MQTT telemetry/event topics.
- Hardware observer that reads service/system/component state without owning
  camera, GPIO, lock, registration, onboarding, or connectivity behavior.

## Proposed Replacement

Hardware keeps ownership of device resources. A telemetry observer builds
canonical v1 envelopes and enqueues them into the existing durable queue for MQTT
delivery. The backend treats MQTT as an unreliable external transport, validates
versioned envelopes, persists idempotently, updates latest health/component
state, deduplicates alerts, and exposes REST APIs from `hardware_devices`.

## Migration and Removal Plan

The authoritative production telemetry path is moved to `hardware_devices`.
Legacy `devices_telemetry` can remain for compatibility, but backend MQTT ingest
for v1 typed telemetry uses `HardwareTelemetryService` instead of writing new
flat rows directly.
