# QBox Connectivity Contract v1

Status: draft  
Last updated: September 1, 2026

This contract defines the production integration boundary for connectivity management between `Qbox-Hardware` and `Qbox-Backend`.

The repositories remain independent codebases. They coordinate only through this versioned contract plus the existing onboarding and MQTT contracts:

- `../device-onboarding/v1.md`
- `../mqtt/device-control-plane-v1.md`

## Ownership

### Backend owns

- user, homeowner, merchant, and admin authorization
- device ownership and assignment checks
- provisioning session authorization
- desired connectivity policy and metadata
- cloud-side device connectivity state
- connectivity history, audit records, and observability
- MQTT command dispatch and acknowledgement tracking
- REST APIs used by mobile apps, admin tools, and service operators

The backend must treat the device as an external client. It must not import hardware source code, run hardware agents, or access device local files.

### Hardware owns

- Wi-Fi radio and network profile management
- NetworkManager integration
- BLE GATT provisioning service
- local Wi-Fi scans
- Wi-Fi credential intake from the local provisioning channel
- DHCP, DNS, internet, and MQTT reachability checks
- local retry, backoff, recovery, and persisted connectivity state
- device-side MQTT client behavior
- device-side command execution and acknowledgement

The hardware repository must not import Django models, serializers, services, settings, migrations, or backend utilities.

### Mobile app owns

- local device discovery over BLE
- collecting Wi-Fi credentials from the homeowner or installer
- requesting backend authorization over HTTPS
- starting an authorized BLE provisioning session
- showing local provisioning progress and cloud connectivity state

The mobile app sends Wi-Fi passwords to the device over the authorized local provisioning channel, not to the backend.

## Non-Negotiable Boundaries

- The backend must never receive, persist, log, or proxy homeowner Wi-Fi passwords.
- Initial local Wi-Fi provisioning must use BLE GATT, not local HTTP or WebSocket APIs.
- HTTP/WebSocket endpoints exposed by a device are not the primary production provisioning channel.
- MQTT is the cloud control plane after the device has network connectivity.
- Repository code sharing is forbidden; shared behavior is represented as schema, topic, endpoint, and state contracts.
- Any breaking contract change requires a new version directory, for example `contracts/connectivity/v2.md`.

## Transport Matrix

| Flow | Transport | Direction | Purpose |
| --- | --- | --- | --- |
| Mobile authorization | HTTPS REST | Mobile -> Backend | Validate user/device permission and create provisioning session |
| Local provisioning | BLE GATT | Mobile <-> Hardware | Scan networks, send credentials, observe connection progress |
| Cloud command | MQTT/TLS | Backend -> Hardware | Request status, forget profile, reconnect, apply policy |
| Cloud telemetry | MQTT/TLS | Hardware -> Backend | Report state, events, diagnostics, command acknowledgements |
| User-visible history | HTTPS REST | Mobile/Admin -> Backend | Read connectivity state, history, and audit |

## REST API Contract

REST APIs are owned by `Qbox-Backend`. They expose authorization, state, and history. They must not expose raw Wi-Fi credentials.

All v1 requests and responses use:

- HTTP header: `X-QBox-Contract-Version: 1`
- JSON field: `schema_version: 1`

### Create provisioning session

`POST /api/v1/devices/{device_uid}/connectivity/provisioning-sessions/`

Purpose: authorize a mobile app or installer to provision a device locally over BLE.

Request:

```json
{
  "schema_version": 1,
  "client_nonce": "base64url-random",
  "requested_transport": "ble",
  "app_instance_id": "opaque-client-id"
}
```

Response:

```json
{
  "schema_version": 1,
  "session_id": "uuid",
  "device_uid": "QBOX-DEVICE-UID",
  "allowed_transport": "ble",
  "expires_at": "2026-09-01T12:00:00Z",
  "ble": {
    "service_uuid": "contract-defined-uuid",
    "session_token": "opaque-short-lived-token",
    "server_nonce": "base64url-random"
  }
}
```

Rules:

- `session_token` must be short-lived and scoped to one device.
- The token authorizes local provisioning only; it is not a device credential.
- The response must not include Wi-Fi SSIDs, passwords, PSKs, or stored network secrets.

### Read connectivity state

`GET /api/v1/devices/{device_uid}/connectivity/state/`

Response:

```json
{
  "schema_version": 1,
  "device_uid": "QBOX-DEVICE-UID",
  "state": "online",
  "network": {
    "ssid": "Home WiFi",
    "security": "wpa2-psk",
    "signal_percent": 86,
    "ip_family": ["ipv4"]
  },
  "checks": {
    "wifi_associated": true,
    "dhcp": true,
    "dns": true,
    "internet": true,
    "mqtt": true
  },
  "last_event_at": "2026-09-01T11:58:00Z",
  "updated_at": "2026-09-01T11:58:10Z"
}
```

Rules:

- SSID may be shown when authorized.
- BSSID, IP address, gateway, DNS server, and similar diagnostics are admin/operator-visible only unless product policy allows broader exposure.
- Wi-Fi secrets are never returned.

### Read connectivity history

`GET /api/v1/devices/{device_uid}/connectivity/events/`

Response:

```json
{
  "schema_version": 1,
  "device_uid": "QBOX-DEVICE-UID",
  "results": [
    {
      "event_id": "uuid",
      "event_type": "wifi_connected",
      "severity": "info",
      "occurred_at": "2026-09-01T11:58:00Z",
      "summary": "Device connected to Wi-Fi and MQTT",
      "metadata": {
        "ssid_hash": "sha256:...",
        "signal_percent": 86
      }
    }
  ]
}
```

Rules:

- Events must be safe for audit logs.
- Do not store plaintext Wi-Fi passwords.
- Prefer hashed or redacted network identifiers for broad visibility.

## BLE GATT Contract

BLE is implemented by `Qbox-Hardware` and consumed by the mobile app. The backend only authorizes short-lived provisioning sessions.

Required BLE capabilities:

- advertise a QBox provisioning service while unprovisioned or explicitly placed in recovery/provisioning mode
- accept a backend-issued provisioning session token
- provide Wi-Fi scan request and scan result characteristics
- accept Wi-Fi credential submission locally
- stream provisioning status updates
- clear sensitive credential material from transient buffers after use

Minimum BLE operations:

| Operation | Direction | Notes |
| --- | --- | --- |
| `authorize_session` | Mobile -> Hardware | Presents backend-issued session token |
| `scan_wifi` | Mobile -> Hardware | Requests local NetworkManager scan |
| `scan_results` | Hardware -> Mobile | Returns SSID/security/signal/channel, no passwords |
| `connect_wifi` | Mobile -> Hardware | Sends SSID and password over encrypted local session |
| `provisioning_status` | Hardware -> Mobile | Reports connection progress and failure reason |

The exact BLE UUIDs and characteristic payload encoding must be documented before implementation and remain under this `v1` contract.

## MQTT Contract

MQTT uses the existing `qbox/v1/devices/{device_uid}/...` namespace from `../mqtt/device-control-plane-v1.md`.

### Connectivity state event

Device publishes to:

`qbox/v1/devices/{device_uid}/state`

Payload:

```json
{
  "message_id": "uuid",
  "device_uid": "QBOX-DEVICE-UID",
  "message_type": "connectivity.state",
  "timestamp": "2026-09-01T11:58:10Z",
  "schema_version": 1,
  "payload": {
    "state": "online",
    "interface": "wlan0",
    "network": {
      "ssid_hash": "sha256:...",
      "security": "wpa2-psk",
      "signal_percent": 86
    },
    "checks": {
      "wifi_associated": true,
      "dhcp": true,
      "dns": true,
      "internet": true,
      "mqtt": true
    }
  }
}
```

### Connectivity event

Device publishes to:

`qbox/v1/devices/{device_uid}/events`

Payload:

```json
{
  "message_id": "uuid",
  "device_uid": "QBOX-DEVICE-UID",
  "message_type": "connectivity.event",
  "timestamp": "2026-09-01T11:58:00Z",

      "ssid_hash": "sha256:...",

  }

```

### Connectivity command

Backend publishes to:

`qbox/v1/devices/{device_uid}/commands`

Payload:

```json
{
  "message_id": "uuid",
  "device_uid": "QBOX-DEVICE-UID",
  "message_type": "connectivity.command",
  "timestamp": "2026-09-01T11:59:00Z",
  "schema_version": 1,
  "payload": {
    "command_id": "uuid",
    "command": "report_connectivity_status",
    "parameters": {}
  }
}
```

Supported v1 commands:

- `report_connectivity_status`
- `restart_connectivity_manager`
- `forget_wifi_profile`
- `enter_ble_provisioning_mode`
- `exit_ble_provisioning_mode`

Dangerous commands, such as forgetting profiles or restarting networking, must require backend authorization and audit records.

### Command acknowledgement

Device publishes to:

`qbox/v1/devices/{device_uid}/command-ack`

Payload:

```json
{
  "message_id": "uuid",
  "device_uid": "QBOX-DEVICE-UID",
  "message_type": "connectivity.command_ack",
  "timestamp": "2026-09-01T11:59:02Z",
  "schema_version": 1,
  "payload": {
    "command_id": "uuid",
    "status": "accepted",
    "result": {
      "state": "online"
    },
    "error": null
  }
}
```

Allowed acknowledgement statuses:

- `accepted`
- `rejected`
- `in_progress`
- `succeeded`
- `failed`
- `timed_out`

## Security Requirements

- Device private keys are generated and stored on the device.
- MQTT uses the device certificate issued during onboarding.
- BLE provisioning sessions must expire and be bound to `device_uid`.
- Wi-Fi credentials must be encrypted in transit over the local provisioning session.
- Wi-Fi credentials must only be persisted in the device network manager profile store.
- Backend logs, audit records, analytics, and support tooling must redact secrets.
- MQTT events should contain redacted SSIDs or hashes unless full SSID visibility is explicitly authorized.
- All command execution must be idempotent where possible and report a final acknowledgement.

## Compatibility Rules

- Additive fields are backward compatible.
- Consumers must ignore unknown fields.
- Removing fields, changing enum meanings, changing topics, or changing authentication semantics is breaking.
- Breaking changes require a new contract version.
- Devices should report their supported connectivity contract version in onboarding capabilities.
