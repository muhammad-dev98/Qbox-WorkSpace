# QBox Device Onboarding Contract v1

Status: active  
Last updated: August 30, 2026

This contract defines the production boundary between `Qbox-Hardware` and `Qbox-Backend` for first-boot onboarding and early steady-state synchronization.

## Principles

- The hardware repository remains an independent client implementation.
- The backend repository remains the control plane and certificate authority boundary.
- No source code is shared across repositories.
- `device_uid` is the canonical device identity.
- Device-specific secrets, private keys, certificates, and bootstrap credentials are never baked into the golden image.

## HTTPS onboarding endpoints

- `POST /api/v1/device-onboarding/bootstrap/`
- `POST /api/v1/device-onboarding/heartbeat/`
- `POST /api/v1/device-onboarding/health/`
- `GET /api/v1/device-onboarding/configuration/`
- `POST /api/v1/device-onboarding/configuration/`
- `GET /mqtt/ca-cert/`

## Contract versioning

- HTTP header: `X-QBox-Contract-Version: 1`
- JSON field: `schema_version: 1`
- MQTT topic namespace: `qbox/v1/...`

Hardware must send schema version `1` on bootstrap and message-envelope based onboarding traffic. Backend responses for onboarding and configuration also expose `schema_version: 1`.

## Bootstrap request

Required fields:

- `schema_version`
- `device_uid`
- `serial_number`
- `csr`

Common optional fields:

- `name`
- `device_id`
- `device_uuid`
- `device_type`
- `version`
- `identity`
- `hardware`
- `software`
- `capabilities`

The CSR common name and SAN URI must both resolve to the same `device_uid`.

## Bootstrap response

The backend returns:

- `status`
- `request_id`
- `schema_version`
- `device`
- `provisioning`
- `certificate`
- `mqtt`
- `next_action`

`certificate` must include:

- `certificate_pem`
- `ca_certificate` when available inline
- `ca_cert_url` as fallback retrieval path

## MQTT namespace

Per-device publish topics:

- `qbox/v1/devices/{device_uid}/telemetry`
- `qbox/v1/devices/{device_uid}/events`
- `qbox/v1/devices/{device_uid}/heartbeat`
- `qbox/v1/devices/{device_uid}/state`
- `qbox/v1/devices/{device_uid}/command-ack`
- `qbox/v1/devices/{device_uid}/configuration-ack`

Per-device subscribe topics:

- `qbox/v1/devices/{device_uid}/commands`
- `qbox/v1/devices/{device_uid}/configuration`

## Security boundary

- Bootstrap uses a temporary per-device bootstrap secret.
- Post-bootstrap HTTP and MQTT traffic use the device certificate and private key generated on the device.
- The backend validates device certificate identity before accepting steady-state onboarding traffic.
- Trusted proxy forwarding of device certificate metadata is allowed only from explicitly configured proxy IPs.

## Golden image constraints

The golden image may include:

- Raspberry Pi OS Lite base configuration
- QBox platform code
- agent code
- packaging assets
- `rpi-image-gen` hooks and overlays
- placeholder non-secret factory config

The golden image must not include:

- real bootstrap secrets
- device private keys
- device certificates
- final device identity values
- production broker credentials
